# Image decode allocation preflight

2026-10-09 root source research, not an implemented image pipeline or measured resource pass. Source is the verified project-private official Go1.27.2 toolchain; no image/private data/cloud request was used.

The current explicit vision PoC in internal/cli/probes.go checks input4MiB, dimensions8192 and pixels16,000,000, accepts PNG/JPEG only, and fully decodes content. This is bounded PoC evidence, not a proof of all production decoder allocations. Product image/GIF handling requires a separate allocation-aware validation gate before actual decode.

JPEG reader.go30..36 retains each component's horizontal/vertical sampling factors. scan.go155..167 computes MCU-rounded dimensions and allocates each progressive component's saved coefficient blocks. dct.go93..95 defines each block as64int32 coefficients: progressive coefficient allocation depends on component sampling and MCU geometry, not just the final visible pixel count. scan.go49 allocates padded YCbCr; scan.go54 additionally allocates black pixels for four-component input. reader.go695 and780 can allocate RGBA conversion while original decoder planes are still live. A generic width*height check therefore does not account for the complete progressive/CMYK/flex peak. Future validation must inspect the supported SOF/sampling fields and calculate all relevant buffers before calling Decode, including rounding/conversion, checked arithmetic and a bounded cumulative estimate. Unknown unsupported layouts must refuse honestly rather than assume one byte per pixel.

GIF reader.go383..420 calls newImageFromDescriptor before decoding every frame. reader.go490..521 allocates a Paletted image for its declared frame bounds; DecodeAll619 retains all frames. Checking only the logical canvas or first frame cannot bound full animation allocation. Future structural preflight must validate every descriptor/range and count cumulative frame pixels and frame count before DecodeAll, without storing an unbounded frame list. Subsequent complete decode remains necessary to prove compressed content is valid.

Cooperative context readers bound waits and check consumed work but cannot force cancellation inside an arbitrary decoder computation or blocked ReaderAt. One admitted operation must retain its slot until actual decode returns. The4MiB input and dimensional/estimated-buffer guards bound admitted work; real512MB/RSS and worst-case elapsed time remain separate native workload gates. No new image limit or production behavior is adopted by this research note.
