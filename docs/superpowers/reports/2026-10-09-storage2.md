## Behavior and decisions

- Schema2 transactionally adds `poll_frames`, `channel_cursors`, and `inbox`; exact manifests1/2 validate snapshots through immutable read-only connections. Unexpected objects, DDL, versions, and foreign version0 files fail before chmod, WAL configuration, or initialization. New zero-byte/nonexistent paths initialize normally.
- A unique account constraint permits one unresolved frame per account, including quarantined frames. Global frames are bounded to4/8MiB, each body2MiB. Record checks the durable prior cursor before committing evidence. Quarantine preserves bytes and cursor and blocks further polls.
- Resolve validates the whole batch (at most256 entries), deduplicates inbox and already claimed message IDs by account/user, enforces1024 entries/8MiB, then commits inbox, cursor and frame deletion together. Capacity/input failures retain the frame and old cursor. CompleteInbox deletes only the scoped consumer reference; callers remain responsible for deciding when processing has finished.
- Frame IDs and inbox sequences use AUTOINCREMENT, preventing a delayed completion/resolution from accidentally addressing newer work after a prior row was deleted. Its standard `sqlite_sequence` object is included in schema2's exact manifest.
- Global facts are capped at10000 and8MiB, preserving the old per-scope10000/4MiB cap. Add and update both enforce global byte caps. Global messages remain10000 and gain64MiB accounting with16KiB reservations for every processing/sending/ambiguous row. Claim is transactional and checks existing scoped claims before capacity. Reservations are implicit in durable states, retained through ambiguity, and released for failed/sent; CompleteMessage replaces the reserved space with a reply bounded to16KiB.
- Root ruling: schema1 data exceeding global facts/message budgets (including pending reply reservations) fails admission with ErrCapacity before writable actions. Exact read-only schema1 snapshot validation still succeeds; no data is deleted or pruned. These legitimate old snapshots require owner reconciliation before migration/restore. Schema1 WAL/SHM sidecars fail admission until the owner produces a completed snapshot/checkpoint; sidecars are never discarded automatically.
- New/migrated schemas are checkpointed before Open returns, so a crash after later poll writes leaves a recognizable schema2 main file plus recoverable WAL. Schema2 admission first recognizes the immutable main manifest, then uses a bounded10s mode=ro effective-WAL preflight to validate the actual manifest and all aggregate quotas before opening writable. Probe close errors are checked. Main-only immutable admission is not treated as evidence about WAL contents.

Byte accounting is payload accounting, not physical SQLite/RSS measurement: facts content; messages content+reply+state reservation; inbox text+context token; raw frames body. IDs, scope/category metadata, indexes, journals, and SQLite page overhead are outside these specified payload budgets. No512MB/VPS claim is made.

## Independent review fix round1/5

Addressed both Important admission findings from the root's independent Medium review. Aggregate quota checks alone admitted exact-schema databases with oversized individual rows, BLOB-affinity TEXT bodies, or a single fact scope exceeding4MiB.

Changes in this round are restricted to the owned `migrations.go`, `inbox.go`, `store.go`, `validate.go`, `migration_test.go`, `inbox_test.go`, and this report. No schema or public API changes.

- Admission now checks each persisted field's SQLite type and byte length using SQL `typeof`/`length(CAST(... AS BLOB))` predicates before loading any row fields into Go. Scope fields are bounded256bytes, message IDs512bytes, fact categories256bytes, text/replies/context/cursors16384bytes. Numeric identity/time fields also require expected SQLite types. Raw bodies require BLOB type and1..2MiB; admission never loads raw body contents into Go.
- Once SQL establishes bounded row sizes, streaming Go checks reuse the scope, fact, message ID and field validators for valid UTF-8, absence of NUL, nonempty scope/ID/fact content and valid state/source/confidence/importance values. Rows are streamed rather than accumulated. Per-field/type/semantic failures return ErrInvalid; aggregate/global/per-scope quota failures return ErrCapacity.
- Legacy and effective schema2 admission both enforce `GROUP BY account,user` fact limits10000/4MiB alongside global10000/8MiB. Individual facts/message content/replies cannot bypass their16KiB bounds through restore or migration. ValidateBackup intentionally remains exact structural/integrity validation; original schema1 snapshots remain valid read-only candidates even when Open rejects unsafe data without mutation.
- Frame byte totals use `length(CAST(body AS BLOB))` both at admission and RecordPoll; TEXT affinity cannot turn byte accounting into character counting.
- PendingPoll and PendingInbox validate receive rows inside the same read transaction used to load the requested payload. Effective mode=ro WAL admission also wraps its manifest, aggregate, SQL shape and bounded Go checks in one read transaction. Thus row sizes cannot change between the SQL guards and bounded scans within either operation.
