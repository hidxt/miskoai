## Boundary and behavior

The existing lexical guard now tracks whether it is admitting the first lexical token after its existing optional initial UTF8 BOM removal. It validates a completely admitted bounded processing-instruction token before releasing a reserved `xml` declaration to `encoding/xml`. The exact target must be lowercase `xml`; any case variant of that exact reserved target refuses. A declaration after whitespace, comment, ordinary PI, element content, another declaration or the root's closing element returns the fixed `ErrInvalid`, with zero public extraction `Result`. Ordinary targets including `xml-stylesheet` and `XML-stylesheet` remain inert bounded PIs; their contents are never fetched or resolved.

The new small deterministic scanner operates on slices of the existing admitted PI. It requires `version` first, optional `encoding` next and optional `standalone` last. Only XML whitespace (space/tab/CR/LF), equals with optional whitespace, paired single/double quotes, and exact lowercase attribute names are accepted. Version `1.0`, case-insensitive `UTF-8`, and standalone `yes`/`no` are the supported values. Well-formed numeric version values outside `1.0` and valid encoding names outside UTF-8 produce fixed `ErrUnsupported`; malformed syntax, unknown/duplicate/reordered fields, missing version, references/extra data, invalid encoding names and invalid standalone values produce fixed `ErrInvalid`. The scanner validates the complete declaration syntax before returning unsupported, so a version `1.1` followed by an unknown field is malformed. Ruling: numeric `2.0` is classified unsupported, consistent with the plan's unsupported-version safe class; it cannot become accepted capability.

All three existing fixed parts use this same guard: `[Content_Types].xml`, `_rels/.rels`, and `word/document.xml`. Existing 16KiB tags, 64KiB PI/text/comment/CDATA tokens, 128 attributes, depth64, ZIP input4MiB/decoded8MiB, complete output128KiB, logical pages64, call-entry cooperative2s and one synchronous Parser admission remain unchanged. No existing test, output policy, source attribution, parser pool, provider/storage/channel/auth/deployment/resource contract or dependency changed.

## FIX ROUND 1 — reserved target delimiters

2026-10-13, same original implementer, ONLY `gpt-6.1-sol` / reasoning effort `medium`; no delegation. Engineering remains **74% (37/50)**. Primary expanded ownership to five files for this correction, adding the existing `internal/document/docx.go` shared safe-token boundary. Main adoption and root acceptance are still primary-owned.

The defect was verified against installed native Go1.27.2 `encoding/xml`: PI target `name()` stops at slash/equal, and the PI parser calls `space()` without requiring that a separator was consumed. Thus `<?xml/?>`, `<?xml=?>`, and `<?XML/?>` become parsed reserved `xml`/`XML` targets with punctuation in their instruction body, while the initial lexical target scanner classified the entire nonwhitespace prefix as an ordinary PI. Each returned successful text in all three fixed DOCX parts. This is a bounded syntax correctness defect, not evidence of new I/O, execution, quota or attribution escape.

The correction uses the actual `xml.ProcInst.Target` in `safeXMLToken` after the existing bounded guard and strict decoder. Exact case-insensitive reserved `xml` targets must be lowercase, then their actual `Inst` must pass the same declaration-body scanner. The scanner was factored into `validateXMLDeclarationBody(body, requireLeadingSpace)`: the lexical path requires initial XML whitespace after the target; the parsed path starts directly at `version` because `encoding/xml` has stripped that whitespace. Attribute order, value grammar and safe-error precedence remain identical. Ordinary declaration placement/uniqueness remains guarded before decoding; punctuation-delimited parsed reserved targets now refuse because their body begins with punctuation or their target casing is reserved. The fallback uses the existing decoder's XML Name grammar rather than copying or narrowing its Unicode rules. No new pool, allocation bound, dependency or resource policy was introduced.

Ruling: `xml:` is a distinct ordinary XML Name target, as are `XML:`, `xml-stylesheet`, `xml.foo`, `xml_foo`, `xml中文`, `xmlλ`, standalone Chinese/Greek targets, and `xmlversion`. They remain inert, including hostile instruction-body data before/after the root. The initial root diagnostic incorrectly asserted `<?xml:?>` invalid; primary explicitly excluded that assertion and required a success control.
