# Serial Runtime Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Root reviews each tested task before the dependent task.

**Goal:** Turn the bounded text agent and persistent inbox into a cancellation-safe serial runtime with private receive evidence.

**Architecture:** One poller, one worker, database-owned work and a bounded wake hint. HTTP/CLI process lifetime is a subsequent subsystem.

**Tech Stack:** Go1.27 stdlib and existing providers/SQLite only.

**Spec:** docs/superpowers/specs/2026-10-09-runtime-design.md.

## Global Constraints
- Go modular monolith; SQLite; one resident process; Linux amd64/arm64 and2C/512MB targets.
- Only GPT-6.1 Medium/Low child configurations; no child delegation.
- No real cloud/WeChat requests or actual private-data service start while owner defers validation; tests are synthetic.
- Fixed QR account/user authorization before model/tools; no ambiguous send retry; no private payload/token in logs or status.
- Poll40s/send15s transport limits remain; raw response≤2MiB;256 messages/batch, opaque/text≤16KiB, bounded32-reference wake channel.

## Review Focus
- Malformed successful poll JSON must survive restart privately before typed decode, without cursor advance.
- Restart with a persisted frame/inbox must process local work before new poll; old claimed messages never repeat model/send.
- Inbox capacity must retry local resolution of the same frame, never repoll prematurely.
- Unauthorized senders/groups/generating messages never reach handler, even if they share IDs with an allowed sender.
- Auth expiry and cancellation stop polling; shutdown joins poller/worker before SQLite close.

## Task2: Serial service — Medium

**Interfaces:**

- `(*Service).Run(ctx context.Context)error` single start, joins fixed poller/worker on return; cancellation returns nil after orderly join. Account auth/quarantine errors pause the poller while management caller can continue until context cancellation.

Counters are current-process only; Received counts normalized authorized entries including duplicate deliveries. Reject negative usage from accumulation and use checked/saturating arithmetic to avoid overflow.
