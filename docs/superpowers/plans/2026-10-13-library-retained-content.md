# Bounded retained library content implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development or executing-plans. Routine internals are owner-authorized; root owns integration/Git.

**Goal:** Preserve explicitly validated prior content for later full restore while counting it against physical quotas and protecting it from active-catalog deletion.

**Architecture:** A bounded owner-private recovery catalog outside the image directory records immutable content identity only. Only a trusted maintenance callback holding Manager admission can add references from an authoritative current snapshot after complete validation. Upload recognizes these records; deletion removes active metadata while retaining protected rollback bytes. No cleanup/adoption/sweep endpoint is added.

**Tech Stack:** Existing Go/privatefs/shared Processor/SQLite DTOs and directory-sync boundary; no dependencies, schema, provider, channel, deployment or512MB policy changes.

**Spec:** docs/superpowers/specs/2026-10-12-private-library-design.md retained physical capacity/full restore; D069/D071. This is recovery groundwork; full bundle/install/Core/Web/reply remain later tasks.

## Global constraints

- Children ONLY gpt-6.1-sol / medium. Engineering74%, no39 credit. All operations synthetic; actual private schema2/live credentials/WeChat/spent cloud untouched.
- Preserve global128 physical objects/64MiB actual bytes, existing128 metadata rows/64MiB declared bytes and4MiB/image limits. Retained/current overlap charges each physical generated key once. No original filename/path from requests.
- Retained objects are introduced only from current authoritative bounded rows plus an already valid catalog, never from arbitrary directory discovery or an imported JSON file. All uncertain objects remain untouched and refuse Upload/retention. Failed/ambiguous identity or durability stays recovery.
- Admission order remains Manager -> actual shared Processor -> fresh Store lease. No caller enters Manager holding Store lease; the maintenance callback may obtain a short Store snapshot lease but must release it before full image validation or retention. No new decoder pool.
- Protected references are kept until future explicit operator reconciliation. This task adds no automatic expiration or deletion of rollback content. File retention can consume capacity and refuse new upload; this is reported honestly.

## Review focus

1. Restart/current empty catalog with known retained files permits safe bounded upload; unknown objects still refuse and remain byte-exact.
2. Malformed/oversized/copy/replaced/linked recovery catalog or missing/corrupt protected bytes cannot authorize adoption/removal.
3. Same key in current/retained catalogs is charged once and must have identical immutable metadata; exact128/64MiB accepted, excess refused before mutation.
4. Active deletion of a protected valid asset removes only metadata; old recovery bytes survive. Unprotected deletion retains current behavior and tombstone/cleanup guarantees.
5. Retention callback and real media/handle/Sync/Close operations join through cancellation/Core future maintenance/Manager.Close; failed writes remove only newly owned stages and never replace uncertain destinations.

Failure before rename cleans only captured original pending if identity still matches; uncertain pending/replaced destination remains recovery and blocks a new retention attempt.
