# Durable bounded attachment envelope Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans task by task. Root dispatch is required; steps use synthetic fixtures only. Receiving attachments in an operational service is a later explicit integration gate.

**Goal:** Preserve one typed encrypted image/file descriptor with genuine user caption and original identity in the existing durable receive queue, without downloading or interpreting it.

**Architecture:** A compatible schema4 companion table references the existing inbox sequence, leaving pinned schema1/2/3 DDL intact. A pure attachment normalizer produces the bounded storage DTO; existing default text receiving stays unchanged until a reviewed attachment-capable handler is wired. Storage never imports media/network and metadata never enters history/export/candidate user evidence.

**Tech Stack:** Go1.27.2 stdlib strict JSON and existing modernc SQLite/private storage; no database/runtime/dependency replacement.

**Spec:** docs/superpowers/specs/2026-10-09-attachments-design.md and docs/research/weixin-media-design-evidence.md at Tencent commit24de5c9eb0dd5e595d7e2d090ed8a3f82870d42c. Root read current inbox/manifest/admission/normalizer/agent/source contracts. This is a plan, not schema adoption, actual migration, receive or resource evidence.

## Global Constraints

- Every child ONLY GPT-6.1 Sol Medium (gpt-6.1-sol, reasoning_effort medium), isolated context, no children, external network, actual private data, credentials, Git or global changes.
- Original scope/ID must be durably claimed before any later download/parser/model/send. This plan performs none of those side effects and never enables an incomplete pipeline.
- Genuine USER text remains only genuine text/caption. Empty caption is allowed with attachment identity; keys/URLs/filenames/extraction/placeholders never populate messages.content or facts/candidates.
- Preserve schemas1/2/3 exactly and existing1024 queue rows/8MiB total byte bound; attachment bytes are INCLUDED, never given a second hidden8MiB quota. Admission precedes Go row materialization. No pruning or unexplained journal deletion.
- One initial encrypted image or file item; additional/voice/video content produces an explicit unsupported descriptor for a future one-reply handler. No selecting an arbitrary first item or falsely claiming content was read.
- Metadata<=16KiB canonical encoded bytes, one completed private descriptor; bytes not payload or authenticity proof. Plaintext4MiB/crypto keys follow the codec plan. CDN still independently validates preferred URL/public DNS before its own request.

## Review Focus

- Duplicate old/new inbox/message identities with changed attachment metadata cannot replace queued data or repeat effects.
- Oversized/malformed/foreign-key-orphan metadata refuses before materialization and cannot hide outside queue quota or alter a legacy snapshot on rejection.
- Unauthorized sender/group/recipient headers and ambiguous consumed aliases must be rejected before key decoding or descriptor admission.
- Attachment-only USER evidence remains empty; summaries/candidate confirmation cannot treat extracted text, URLs, names or fallback descriptions as user statements.
- Cancellation/fault during atomic resolve/complete preserves either the original raw frame/cursor or a complete inbox+descriptor; it never leaves detached metadata.

## Root downstream gate

This package is durable data and pure normalization only. The later agent pipeline must forward the DTO, allow empty caption only with validated attachment, durably ClaimMessage before Download, retain one actual media/parser admission, use shared vision transport, label bounded document excerpts, keep original USER provenance, and reuse one strict-ACK send. Reject/failed/ambiguous outcomes stay durable and cannot replay. Default service activation waits for that complete local/review/native gate. Existing paid allowance is spent; additional live media/model tests require their own bounded authorization. No real migration/private startup/WeChat image/GIF/512MB/final acceptance is authorized or claimed by this plan. Schema4 evolution uses the existing SQLite route; a database-route/quota/safety/target scope change requires owner approval, not an internal plan assumption.
