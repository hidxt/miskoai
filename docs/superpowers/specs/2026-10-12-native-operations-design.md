# Native binary operations design

2026-10-12. Implements the already authorized master task4/20/21/26 and package41. Engineering72%; no server access or release permission follows this design. Root uses brainstorming/writing-plans; owner's continuous-development instruction supplies routine design authority.

Ship a reviewed user systemd service template and an operator guide for the existing native Linux amd64/arm64 executable. This completes operations packaging, not deployment, release or 512MB acceptance. Runtime remains one Go process and SQLite; no new application code, supplier, resource limit, automatic installer or additional server runtime.

Use the user's systemd manager as the default, with executable `%h/.local/bin/miskoai`, private data `%h/.local/share/miskoai`, private configuration `%h/.config/miskoai`, and unit installed at `~/.config/systemd/user/miskoai.service`. Explicitly explain login lifetime and optional administrator-approved lingering; do not run it. Alternative system-wide policy is future administrator work, not a second untested template.

The template uses `Type=simple`, `ExecStart=... serve`, fixed loopback `127.0.0.1:8080`, `UMask=0077`, `NoNewPrivileges=true`, a required private EnvironmentFile, `KillSignal=SIGTERM`, `KillMode=control-group`, finite120s `TimeoutStopSec`, `Restart=on-failure` with10s delay and bounded start attempts. Explain that stop timeout may force termination and cannot prove graceful cleanup. Avoid unsupported per-user mount-namespace directives and unmeasured MemoryMax/CPU limits. No secrets in unit arguments or checked-in values. EnvironmentFile is0600 and private parent0700; credentials JSON also0600/owned by runtime user. The guide's example environment file contains only paths/configuration and an unmistakable synthetic password placeholder; replace in a local editor before start. Provider keys use the existing `MISKOAI_CREDENTIALS_FILE` interface, not shell arguments.

Installation is manual from a supplied, independently verified native artifact. Until final artifact/release gate, development cross-builds are clearly development-only. Verify architecture, SHA256 against trusted published checksums when available, `version`, `licenses`, and synthetic `doctor`; no curl-to-shell or implicit download/start. Create only the explicitly listed new user-owned directories, refuse preexisting unexpected paths/symlinks, and initialize once without clobbering settings. Existing settings/env precedence and DeepSeek `deepseek-flash` are preserved. Document that `serve` may process private account traffic and must only be started after explicit operator readiness; this development task never starts it.

Upgrade: stop/join, create a consistent stopped SQLite backup with the existing CLI and exclusive data lock, separately preserve private settings/authorization and any future library files, verify the new binary, retain old binary, install, validate, then consciously restart. Binary rollback alone cannot undo a schema migration. Database rollback uses validated restore, retains prior DB, and pauses external channels pending explicit reconciliation. Never copy live DB/WAL or delete unexplained journals; never suggest automatic rollback/re-send.

Uninstall: stop/disable/remove only the installed unit and binary after ownership/path verification. Keep data, backups and configuration by default. Private-data deletion requires an explicit separate owner decision; no recursive-delete recipe is supplied. SSH loopback tunnel remains the remote management path. Troubleshooting uses safe enum/status/doctor output and permissions, with no private environment/file dump.

Verification: parent reads every command/template field and checks agreement with actual CLI/config/privatefs/maintenance source. Native Windows development build/`version`/`licenses`/synthetic `doctor` prove the existing executable contracts only. `systemd-analyze --user verify` and actual systemd startup/shutdown are recorded only if a real native Linux environment runs them; absent Linux/server evidence is honestly unverified. No superficial implementation-mirroring unit tests for documentation. Independent Medium review checks lifecycle, privacy, upgrade recovery and platform assumptions.
